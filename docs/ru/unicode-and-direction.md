# Unicode и направление текста

Библиотека хранит и возвращает байты, так что UTF-8 проходит через неё
нетронутым. Эта страница о местах, где байтов недостаточно: подсчёт и
обрезка текста, языки, которые пишутся справа налево, и предложения, где
смешаны оба направления.

- [UTF-8 хелперы](#utf-8-хелперы)
- [Направление текста](#направление-текста)
- [Текст в двух направлениях](#текст-в-двух-направлениях)

## UTF-8 хелперы

Считать символы это не считать байты:

```c
strlen("Привет");            /* 12 */
ci18n_utf8_length("Привет");  /* 6  */
```

А обрезка строки под буфер может попасть в середину символа, и получатся
байты, которые не примет ни один декодер. `ci18n_utf8_truncate` режет только
по границе символа:

```c
char label[16];

ci18n_get_copy("title", label, sizeof(label));
ci18n_utf8_truncate(label, sizeof(label) - 1);
```

Бюджет это длина текста без завершающего нуля, так что `char[16]` берёт
`sizeof(buffer) - 1`. Результат может выйти на три байта короче бюджета,
потому что разрез сдвигается назад, а не делит символ. Ничего не
дописывается, так что если нужно многоточие, место под него есть.

Обрезайте до копирования в меньший буфер, а не после: копия, обрезанная на
последнем байте, уже помещается, и `ci18n_utf8_truncate` нечего чинить.
Правильный порядок показывает [examples/embedded_ui](../../examples/embedded_ui/).

`ci18n_format` и родственные функции уже делают это за вас; см.
[Форматирование](formatting.md#буферы-и-обрезка).

Проверка строгая, в том смысле, которого требует стандарт Unicode:

```c
ci18n_utf8_valid(text);
```

Она отвергает всё, что не является UTF-8, а не только то, что не
декодируется: символ, записанный большим числом байт, чем нужно, половинку
суррогатной пары от U+D800 до U+DFFF, всё выше U+10FFFF, байт продолжения
без ведущего байта и последовательность, на середине которой строка
кончается. Снисходительные декодеры это способ обойти проверку одного
представления другим. Проверяйте текст, который пришёл снаружи, например
пакет языка, полученный по сети, до загрузки.

Чтобы пройти строку по одному символу:

```c
for (const char *p = text; *p; p += ci18n_utf8_sequence_length(p))
{
    /* p points at one whole character */
}
```

Такой цикл никогда не зависнет: на некорректном байте функция вернёт 1 и
шагнёт через проблему, а не будет крутиться на ней вечно.

Одно честное ограничение. «Символ» здесь это одна кодовая точка Unicode. Для
ограничения длины это полезный ответ, но всё ещё не то число, которое
насчитал бы читатель. Ударение, записанное отдельным комбинируемым знаком,
это своя кодовая точка, а одно эмодзи может состоять из нескольких.
Подсчитать их можно только по графемным кластерам, а для этого нужна база
символов Unicode, то есть ровно те данные, которых эта библиотека не
поставляет.

## Направление текста

Арабский, иврит и персидский пишутся справа налево, и интерфейсу нужно
знать, как располагать элементы. Направление это свойство языка, поэтому на
этот вопрос отвечает библиотека; раскладка ваша.

```c
ci18n_set_current("ar");

ci18n_current_direction();                        /* CI18N_DIR_RTL */
ci18n_direction_name(ci18n_current_direction());  /* "rtl" */
```

Названия те же, что в HTML и CSS, так что подставляются как есть:

```c
printf("<html lang=\"%s\" dir=\"%s\">\n",
       ci18n_get_current(),
       ci18n_direction_name(ci18n_current_direction()));
```

`ci18n_direction(code)` отвечает для любого кода, не трогая текущий язык.
Подтег письменности решает сам, потому что направление принадлежит
письменности, а не языку:

| Код | Направление | Почему |
| --- | --- | --- |
| `ar`, `ar-EG`, `ar_EG.UTF-8` | rtl | арабский, регион и кодировка не важны |
| `he`, `fa`, `ur`, `ps`, `dv`, `yi`, `ckb` | rtl | письменность по умолчанию справа налево |
| `ku`, `az`, `pa` | ltr | латиница или гурмукхи, если не сказано иное |
| `az-Arab`, `pa-Arab`, `ku-Arab` | rtl | подтег письменности важнее |
| `ar-Latn` | ltr | арабский латиницей читается слева направо |
| `xx`, `""`, `NULL` | ltr | неизвестный язык, и слева направо это безопасная догадка |

Неизвестный язык считается левым. Это и более частый ответ, и более
безопасный: левый интерфейс, показанный справа налево, сломан так, что этого
не пропустит никто, а обратное лишь выглядит непереведённым.

## Текст в двух направлениях

Значение, написанное в другую сторону, переставляет фразу вокруг себя.
Английское имя внутри арабского текста утаскивает запятую после себя не на ту
сторону, а имя на иврите в английской фразе может поменяться местами с
соседним числом. Лечится изоляцией каждого значения: тогда отрисовщик
раскладывает его отдельно.

```c
ci18n_set_bidi_isolation(true);
ci18n_format(out, sizeof(out), "inbox", "name", "Sam", NULL);
/* "{name}، لديك..." becomes FSI "Sam" PDI "، لديك..." */
```

Каждое значение, которое подставляют `ci18n_format` и родственные функции,
включая `{count}` и вывод форматтеров, оборачивается в FSI и PDI. Это два
невидимых символа, их понимают браузеры, GTK, Qt, Android и iOS. Текст,
написанный переводчиком, не оборачивается никогда. Настройка своя у каждого
каталога и по умолчанию выключена: включайте её для текста, который читают
люди, и не включайте для логов и всего, что разбирает программа, ведь маркеры
это настоящие байты, по 3 на каждый.

| Для чего | Что взять |
| --- | --- |
| Значение, вставленное без `ci18n_format` | `ci18n_bidi_isolate(out, cap, text)` |
| Строка, кончающаяся числом или символом | дописать `ci18n_bidi_mark(dir)`, LRM или RLM |
| Сами символы | `CI18N_FSI`, `CI18N_PDI`, `CI18N_LRM`, `CI18N_RLM` |

Это разметка для отрисовщика, который сам выполняет алгоритм Unicode bidi.
Библиотека алгоритм не выполняет, так что контроллеру дисплея, который рисует
байты слева направо по порядку, всё равно нужен свой шаг bidi.
